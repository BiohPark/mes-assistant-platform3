# 실제 환경 검증 절차서 (양식)

작성일: 2026-09-26 · 상태: **절차 준비 — 아직 실행하지 않음**

사내 OpenWebUI에 실제로 연결했을 때 파일·대화 컨텍스트 전달이 설계([fusion-design.md](../fusion-design.md))대로 동작하는지, 그리고 assistant가 자료를 실제로 이해하는지를 확인하기 위한 절차다.

- 모의 API 검증(가짜 OpenWebUI 경로)을 통과했다고 이 절차의 결과를 대신할 수 없다.
- 이 문서에 **사내 주소·API 키·실제 업무 자료·실명**을 적지 않는다. 결과 기록에도 옮기지 않는다. 스크린샷과 원본 로그는 저장소 밖에 둔다.
- 설치된 OpenWebUI 버전에 따라 화면·설정 이름·응답 형식이 다를 수 있다. 아래의 경로와 필드는 **확인 대상**이지 보장된 사양이 아니다.

## 1. 전제조건

| # | 항목 | 확인 |
|---|---|---|
| P1 | 검증에 쓸 테스트용 계정과 API 키가 있다. 키는 앱 설정 화면에만 입력하고 어디에도 기록하지 않는다 | ☐ |
| P2 | 설치된 OpenWebUI 버전을 기록했다(결과표 머리에 버전만 적는다) | ☐ |
| P3 | 데모를 브라우저에서 직접 호출하는 경우, 서버가 데모의 출처(origin)에 CORS를 허용한다. 새 저장소처럼 서버가 대리 호출하면 이 항목은 해당 없다 | ☐ |
| P4 | 검증할 assistant(모델 ID)를 정했고, 에이전트 관리 화면에서 매핑했다 | ☐ |
| P5 | 아래 3장의 **가상 자료**를 준비했다(실제 업무 자료 사용 금지) | ☐ |
| P6 | 브라우저 개발자 도구의 네트워크 기록을 켰다. 요청 본문 확인용이며 키가 담긴 헤더는 기록에 옮기지 않는다 | ☐ |

## 2. 연결과 API 형태 확인

각 항목은 "기대 동작"이 실제 응답과 맞는지 확인하고, 다르면 실제 형태를 요약해 적는다(주소·키 제외).

| # | 확인 항목 | 기대 동작 (설계 가정) | 결과 |
|---|---|---|---|
| C1 | 모델 목록 조회 | `{baseUrl}/models`가 모델 ID 목록을 돌려준다 | |
| C2 | 채팅 스트리밍 | `{baseUrl}/chat/completions`가 SSE로 응답하고 `[DONE]`으로 끝난다 | |
| C3 | 파일 업로드 | `POST /api/v1/files/`(multipart)가 `id`를 포함한 JSON을 돌려준다 | |
| C4 | 파일 처리 상태 | `GET /api/v1/files/{id}/process/status`가 존재한다. 상태 값의 종류(예: 처리 중·완료·실패)를 기록한다. 없으면(404) 그 사실을 기록한다 | |
| C5 | 처리 시간 | 작은 텍스트 파일, 약 1MB PDF, 여러 파일 동시 선택 각각의 처리 완료까지 시간 | |
| C6 | `files` 파라미터 | 채팅 요청의 `files: [{type: "file", id}]`를 받아들이고, 답변이 파일 내용을 반영한다 | |
| C7 | 처리 전 첨부 | 처리가 끝나기 전에 첨부하면 어떻게 되는지(오류 / 내용 누락 / 대기) | |
| C8 | 실패 응답 | 지원하지 않는 형식·용량 초과 파일을 올렸을 때의 응답 코드와 메시지 | |
| C9 | 업로드 파일 이름 | 버전을 붙인 이름(예: `URS_DEMO (v2).md`)이 assistant 쪽 출처 표시에 그대로 보이는지 | |

## 3. 가상 검증 자료

**모두 가상의 내용**으로 만든다. 각 자료에는 질문으로 확인할 "심어 둔 사실"을 문서의 앞·중간·끝에 나누어 넣는다. 검색 기반 부분 전달일 때 중간·끝의 사실이 빠지는지를 보기 위해서다.

| 자료 | 형식 | 심어 둔 사실 (예시) |
|---|---|---|
| D1 `URS_DEMO.md` v1 | Markdown | 앞: 요구사항 ID `REQ-DEMO-07` / 중간: 알람 보관 기간 **90일** / 끝: 승인 부서 "가상 품질팀" |
| D2 `URS_DEMO.md` v2 | Markdown | D1과 같되 중간 값만 **120일**로 변경 |
| D3 `FDS_DEMO.pdf` | 텍스트 추출 가능한 PDF | 중간: 화면 ID `SCR-DEMO-12`, 끝: 재시도 횟수 **3회** |
| D4 `TEST_DEMO.xlsx` | 스프레드시트 | 두 번째 시트: 시험 항목 **17개** |
| D5 참조용 대화 | 데모 안의 다른 대화(같은 태그) | 대화 중간 턴에서 합의한 값: 배치 크기 **250** |

## 4. 전달 방식과 이해 확인

질문은 새 대화에서 한 번에 하나씩 하고, 매번 "전송 기록"(요청 기록)을 함께 저장한다.

| # | 설정 | 질문 (예시) | 기대 답 / 근거 | 보는 것 |
|---|---|---|---|---|
| U1 | D1만 ★ 선택, 첨부 방식 | "알람 보관 기간은?" | 90일 / D1 중간 | 첨부 파일의 중간 내용이 전달되는가 |
| U2 | D1만, 첨부 방식 | "승인 부서는?" | 가상 품질팀 / D1 끝 | 문서 끝까지 전달되는가(전체 전달인지 검색 기반 부분 전달인지) |
| U3 | D1 ★ + D2 ☑ | "보관 기간은 며칠인가? 자료 간 차이가 있으면 알려줘" | 주 입력 90일, 참고 자료는 120일이라고 구분 | ★ 의미와 버전 구분이 전달되는가 |
| U4 | D2 ★ + D1 ☑ | 위와 같음 | 주 입력 120일 | ★를 바꾸면 우선순위도 바뀌는가 |
| U5 | D3만 | "재시도 횟수는?" | 3회 / D3 끝 | PDF 본문 이해 |
| U6 | D4만 | "시험 항목 수는?" | 17개 / D4 두 번째 시트 | 스프레드시트 이해 |
| U7 | D5 대화를 통째 선택 | "합의한 배치 크기는?" | 250 / D5 중간 턴 | 대화 원문 인라인 전달 |
| U8 | D1~D4 모두 선택 | "각 자료의 핵심 ID를 나열해줘" | REQ-DEMO-07, SCR-DEMO-12 등 | 복수 파일 처리 시간·누락 여부 |
| U9 | 선택 없이 태그만 공유 | "보관 기간은?" | 모른다고 답해야 함 | 선택하지 않은 자료가 전달되지 않는가 |
| U10 | 한도를 넘게 선택 | 전송 시도 | 전송이 막히고 안내가 뜸 | 자동 절단·자동 요약이 없는가 |

설치 버전에 "문서 전체 전달"과 "검색 기반 전달"을 고르는 설정이 있으면, 설정 이름과 값을 기록하고 U1·U2를 두 설정에서 모두 확인한다.

## 5. 판정 기준

| 판정 | 기준 |
|---|---|
| 통과 | 기대 답과 같고, 근거 자료(또는 위치)를 맞게 언급한다 |
| 부분 | 답은 맞지만 근거가 불명확하거나, 여러 사실 중 일부만 맞는다 |
| 실패 | 틀린 답, 자료를 받지 못했다는 응답, 자료에 없는 내용을 지어냄 |
| 판단 불가 | 연결 오류·처리 실패 등으로 질문까지 가지 못함(원인을 C 항목에 기록) |

U9·U10은 "전달되지 않음 / 전송이 막힘"이 통과다.

## 7. 결과 해석과 후속 조치

- U2가 실패하고 U1이 통과하면 검색 기반 부분 전달일 가능성이 높다 → ★ 파일의 전체 전달 방식(설정 또는 본문 인라인)을 재검토한다.
- U3·U4가 실패하면 ★ 의미가 전달되지 않은 것이다 → 라벨 문구·파일 순서·버전 이름을 조정하고 다시 확인한다.
- C4가 없거나(404) C7에서 내용이 누락되면 처리 완료 판정 방식을 설치 버전에 맞게 조정한다.
- 결과는 [fusion-design.md](../fusion-design.md)의 미확정 정책(§6, 특히 7·11)을 확정하는 근거로 쓴다.
