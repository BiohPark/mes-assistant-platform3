# 융합 설계 — platform2 × Codex 비교와 보완

작성일: 2026-09-26 (KST) · 상태: **설계 문서 (구현 아님)**

이 문서는 `mes-assistant-platform2`(이 저장소, 기준)의 설계를, 형제 저장소 `mes-assistant-platform`(Codex 작업)의 **실제 코드**와 Codex 설계안(`docs/codex-demo-integration-design-comparison.md`, 구현되지 않은 아이디어 문서)에 비추어 보완한 결과다.

- 전제: 이 저장소는 **데모로 마무리**하고, 실제 구현은 **별도 저장소**에서 진행한다.
- 이 문서만으로 구현을 시작하지 않는다. 구현은 별도 요청과 실행 계획으로 진행한다.
- 검증 범위는 **모의 API 검증 + 실제 환경용 검증 절차 준비**까지다. 실제 OpenWebUI의 파일 이해·답변 품질을 검증했다고 해석하지 않는다. 절차서: [evaluation/real-env-verification.md](evaluation/real-env-verification.md)

## 0. 읽는 법

**근거 표기**

| 표기 | 의미 |
|---|---|
| **[기록]** | 과거 문서(HANDOFF 등)에 남은 검증 결과. 이번에 다시 실행하지 않았다 |
| **[확인]** | 이번 작업에서 소스 코드를 읽어 확인한 사실. **P2 `6389190`, CX `57207c0` 기준**. 테스트·빌드·브라우저는 실행하지 않았다 |
| **[추론]** | 코드에서 추론했으나 실행으로 확인하지 않은 것 |
| **[제안]** | 아직 구현하지 않은 설계 |

**경로 표기**: `P2 src/...` = 이 저장소, `CX src/...` = `mes-assistant-platform` 저장소 루트 앱(`legacy/`, `agent-hub-demo/` 제외). 줄 번호는 위 커밋 기준이다.

**최우선 원칙 — 사용자 정정** (CX 설계안 §2에서 사용자가 직접 선택한 내용)

- 단계·선후 관계·에이전트 순서를 참조 조건으로 쓰지 않는다. 순서 기반 인계, 고정 워크플로우, 자동 후속 실행을 만들지 않는다.
- **같은 태그를 직접 공유하는 대화를 파일처럼 통째로 체크**하고, 필요하면 메시지 선택·요약 같은 세부 조절을 한다.
- 대화를 체크하면 **전체 원문**이 기본이다. 한도를 넘으면 범위 선택이나 요약을 안내한다.
- **자동 절단·자동 요약·참조 대화의 재귀 수집을 하지 않는다.**

이전 platform2 계획의 "인계 메모"와 "다음 단계로 넘기기"는 이 원칙과 충돌하므로 폐기한다(§3).

## 1. 진행 방식 판단 — 데모 완성(경우 1) vs 바로 새 저장소(경우 2)

판단 기준은 데모에 들이는 작업이 새 저장소로 **이월되는가, 버려지는가**다.

| 이월됨 (새 저장소 프론트가 platform2 코드에서 출발할 경우) | 버려짐 (서버가 대체) |
|---|---|
| 화면·UX 흐름, React/shadcn 컴포넌트 | Dexie 스키마·마이그레이션·저장소 구현 |
| 도메인 순수 함수: `tags`·`sharedPool`·`kanban`·`titles`·`modelResolution`·`reporting` | 브라우저 lease/heartbeat/epoch, 탭 간 동시성 보호 |
| 프롬프트 조립(`llm/context.ts`), SSE 파서, 개발용 Mock provider | IndexedDB 백업 형식·복원 검증 |
| 평가 시나리오·테스트 케이스, 확정된 정책 | 브라우저의 API 키 보관, CORS에 의존하는 직접 호출 |
| 데이터 계약·DDL 초안(문서) | IndexedDB 파일 저장소 구현체 |

| | 경우 1: 데모 완성 → 테스트·보완 → 새 저장소 | 경우 2: 지금 바로 새 저장소 |
|---|---|---|
| 장점 | 새 UX(대화 선택·요청 트레이·크기 한도)를 현업과 적은 비용으로 검증. 데모가 살아 있는 명세가 됨 | 중복 투자 없음. 동시성·키·CORS·파일 저장이 서버에서 자연스럽게 해결됨 |
| 단점 | 저장 계층 정규화(약 75파일)와 요청 lease(약 24파일)가 대부분 버려짐 | 검증 안 된 UX를 전제로 백엔드 스키마를 설계할 위험 |
| 적합한 상황 | 새 저장소 착수가 수개월 뒤이고, 그동안 데모를 현업이 실제로 씀 | 같은 팀이 수주 안에 착수하고, UX를 새 저장소 첫 반복에서 검증해도 됨 |

**추천 — 경우 2를 기본으로, 짧은 UX 검증 스프린트를 거친다 (2-b)**

1. 데모에서는 **이월되는 것만** 한다(약 25–35파일).
   - 새 UX 프로토타입: 자료 패널의 "대화" 섹션, 컴포저 위 "이번 요청에 사용" 트레이와 크기 게이지, 답변별 "사용한 자료"와 앱 내 전송 기록 뷰어
   - 시연을 깨는 결함 4건 수정: 첨부가 1회만 전달됨, SR 첨부 누락, 산출물 버전 체인이 안 생김, 입력창 잠김
   - API 키가 백업에 포함되는 문제 차단
2. 저장 계층 전면 정규화, lease·fencing, 파일 저장소 구현체는 데모에서 하지 않는다. §8의 데이터 계약·DDL·API 문서로 옮기고 새 저장소에서 서버 기준으로 구현한다.
3. 현업 2–3명이 대표 과업(§6 E6)으로 시험해 미확정 정책(§5)을 확정한 뒤 데모를 동결한다(예: 태그 `demo-final`).
4. 새 저장소: 서버(TypeScript 풀스택 — NestJS, D20) + DB + **파일은 디스크·NAS에 파일 그대로**. 프론트는 platform2의 `domain`·`llm`·`components`·`features`를 이식하고, `db/repositories`는 같은 시그니처의 API 클라이언트로 바꾼다. 착수 자료: [next-project/](next-project/README.md)

경우 1을 그대로 하는 것은 "새 저장소 착수가 한참 뒤이고 데모를 실사용"할 때만 권한다.

## 2. 두 프로젝트 비교 — 코드 근거

### 2.1 파일 업로드와 AI 전달

## 5. 대화 컨텍스트 설계 [제안]

### 5.1 후보

- 현재 대화와 `tagKey`를 하나 이상 **직접** 공유하는 다른 대화만 후보다. 자기 자신과 간접 연결(A–B, B–C만 있을 때 A에서 C)은 제외한다.
- 최근 활동순으로 보여 준다. 에이전트는 칩으로만 표시하고 "이전/다음 단계" 같은 표현은 쓰지 않는다.
- SR 접수 대화는 후보에서 제외한다. SR 본문과 첨부로 대신하고, 요청자와의 대화를 보호한다.
- 태그는 발견 조건이지 권한이 아니다. 새 저장소에서는 열람 권한을 서버에서 다시 검사한다.

### 5.2 선택 단위와 모드

파일과 같은 행 패턴(☑ 선택, ★ 주 입력, 출처, 크기, 미리보기)을 쓴다.

| 모드 | 내용 |
|---|---|
| `full` (기본) | 선택 시점까지의 적격 메시지 **전체 원문**. 적격 = 사용자·assistant 역할, 완료 상태, 팀 의견이 아닌 것. system·실패·미완성 응답은 제외 |
| `messages` | 선택 대화상자에서 개별 메시지 또는 "여기부터/여기까지" 범위를 고른다. 전달될 내용을 미리 보여 준다 |
| `summary` | 사용자가 누르면 보조 요청으로 만들고, 미리보기·편집을 거쳐 적용한다. 요약 요청 자체가 한도를 넘으면 메시지 범위를 줄이도록 안내한다. 자동 분할 요약은 하지 않는다. Mock에서는 "대역"으로 표시한 규칙 추출 |

### 5.3 고정과 갱신

- 선택하면 `ContextSnapshot`을 만든다.
  - `full`·`messages` 모드는 메시지 ID 목록과 경계(`upToMessageId`)만 저장하고 **내용은 복사하지 않는다**. 완료된 메시지는 바뀌지 않기 때문이다(§2.2).
  - `summary` 모드는 요약 본문과 출처(원본 메시지 ID·모델·작성자·수정자)를 저장한다.
- 원본 대화에 새 메시지가 생기면 "새 메시지 N · 갱신"을 표시한다. 갱신하면 새 스냅샷을 만든다.
- 요청을 시작할 때 사용한 스냅샷 ID를 요청 기록에 고정한다. 선택 해제나 갱신은 다음 요청부터 반영된다.

### 5.4 재귀 금지와 한계

- 참조 대화 **자신의 메시지만** 전달한다. 그 대화가 입력으로 쓴 파일, 그 대화가 참조한 다른 대화, 요청 스냅샷, system 프롬프트는 모으지 않는다. 필요한 파일은 사용자가 따로 선택한다.
- 한계: 원본 답변에 이미 다른 대화의 내용이 섞여 있을 수 있다. 이 설계는 그런 간접 전파까지 막거나 정보 출처를 완전히 증명하지 않는다.

### 5.5 프롬프트 배치

- 현재 대화의 발화로 합치지 않는다. 주입 가드(`INJECTION_GUARD`) 뒤의 `## 참조 대화 (N)` 절에 참고 데이터로 넣는다.
- 머리글: `### [주 입력|참고] WK-… · 에이전트 · "제목" — 메시지 12개 · 선택 시점 …`
- 본문: `[사용자 · 이름] …` / `[assistant] …`. 항상 인라인이다. 원문 전체를 전달하는 것이 목적이므로, 검색 기반 부분 전달이 될 수 있는 파일 첨부 방식은 쓰지 않는다.
- 업무 역할 지침은 넣지 않는다(D9).

### 5.6 삭제 보호

다른 대화가 입력으로 참조하는 대화는 삭제를 막는다. 입력으로 쓰이는 파일에 적용하는 규칙과 같다.

### 5.7 데이터 모델 초안

| 모델 | 필드 | 비고 |
|---|---|---|
| `ConversationInput` | `id, taskId, sourceTaskId, weight('main'\|'reference'), mode, snapshotId, sortOrder, selectedBy, selectedAt` | unique(`taskId`, `sourceTaskId`) |
| `ContextSnapshot` | `id, sourceTaskId, mode, messageIds[], upToMessageId, bytes, summaryText?, summaryModel?, createdBy, createdAt, editedBy?, editedAt?` | 불변. 갱신 = 새 행. DB에서는 `messageIds[]` → 자식 테이블 `context_snapshot_message(snapshot_id, message_id, seq)` |
| `RequestRecord.inputs[]` | 공통 `kind('file'\|'conversation')` / 파일: `fileId, version, weight, source, oneShot, delivery('attached'\|'inline'\|'metadata_only'\|'failed'), remoteId?, error?` / 대화: `sourceTaskId, snapshotId, mode, messageCount, bytes` | 요청 시작 시 고정. API 키 없음 |

### 5.8 크기 한도

- 직렬화한 요청 본문 전체의 바이트로 잰다. 기본 256 KiB이고 설정에서 조정할 수 있다. OpenWebUI에 첨부로 올리는 파일 바이트는 여기에 포함되지 않는다고 표시한다.
- 컴포저 위 트레이의 게이지는 선택 항목·작성 중인 글·대화 이력으로 실시간 계산한다(예: `예상 180 KB / 256 KB`).
- 한도를 넘으면 전송 버튼을 막고 사라지지 않는 안내를 보여 준다. 동작: [입력 해제] [메시지 범위 선택] [요약 만들기] [새 대화로 이어가기(이 대화를 참조로 선택)]
- 바이트 한도는 모델의 토큰 한도와 다르다. 한도를 통과했다고 모델 컨텍스트에 들어간다고 보장하지 않는다.

### 5.9 화면

| 위치 | 내용 |
|---|---|
| 자료 탭 | "파일 \| 대화" 두 섹션. 같은 행 패턴. 대화 행: 에이전트 칩·코드·제목·상태·공유 태그·메시지 수·크기·"새 메시지 N"·"태그 해제됨" |
| 대화 선택 대화상자 | 모드(전체 / 메시지 선택 / 요약), 메시지 목록과 범위 지정, 전달 내용 미리보기, 크기. 좁은 화면에서는 전체 화면 시트 |
| 컴포저 위 트레이 | "이번 요청에 사용 · N" — 파일과 대화 칩(★/☑ 전환, ×), 전달 방식 배지(첨부/본문/이름만), 크기 게이지, 오류 항목 옆 복구 버튼. 좁은 화면에서는 "자료 N" 칩으로 접힘 |

| 1 | 대화 선택 시점 | **고정**: 미리 본 것이 곧 전송되고 재현할 수 있다. 파일 버전 고정(D6)과 일관된다. 갱신을 잊을 수 있다 / **전송 시 최신**: 단순하고 항상 최신이지만 미리보기와 실제 전송이 달라지고 진행 중인 원본이 섞인다 | 고정 + "새 메시지 N · 갱신" |
| 2 | 태그 해제 후 선택 | **유지**: 예기치 않은 유실이 없지만 관계없어진 자료가 계속 갈 수 있다 / **자동 해제**: 깔끔하지만 사용자가 모르게 사라진다 | 유지 + "태그 해제됨" 배지. 전송 시 존재·열람 가능 여부를 다시 검사 |
| 3 | 적격 메시지 | 팀 의견 포함 여부 | 제외(현재 대화의 이력 규칙과 같게) |
| 4 | 대화에 ★ 허용 | 파일과 같은 패턴 | 허용, 여러 개 가능(두 프로젝트 모두 복수 ★) |
| 5 | 한도 단위 | 바이트(단순) / 토큰(모델별 토크나이저 필요) | 바이트 256 KiB. 토큰 예산은 미확정으로 남긴다 |
| 6 | 요약 보관 위치 | 스냅샷 / 파일(산출물) | 스냅샷. 파일로 공유하려면 기존 "산출물로 저장"을 쓴다 |
| 7 | 파일 전달 실패 | **자동 인라인(D10)**: 편하지만 AI가 받은 것이 달라진다 / **중단 + 선택**: 정직하지만 한 번 더 눌러야 한다 | 중단 + 실패 항목 옆에서 선택. **D10 변경 — 사용자 확인 필요** |
| 8 | 컴포저 첨부 | 이번 메시지만 / 대화 입력으로 고정 | 고정(☑) + 칩에서 "이번 메시지만"으로 전환. OpenWebUI 채팅에서도 첨부가 대화 동안 유지되는 것과 같다 |
| 9 | 재시도 입력 | 실패 당시 스냅샷 / 현재 선택 | 현재 선택(트레이에서 보인다). 사용자 메시지는 재사용해 한 번만 보낸다 |
| 10 | 원격 파일 ID | 기록하지 않음 / 감사 기록 | 요청 기록에는 보존. 재사용 캐시는 따로 두고 백업에서 제외 |
| 11 | OpenWebUI 업로드 시점 | 전송할 때 / 선택할 때 미리 | 전송할 때. 미리 처리 여부는 실제 환경에서 처리 시간을 잰 뒤 판단 |
| 12 | 후보 정렬 | 에이전트 순서 / 최근 활동 | 최근 활동(순서처럼 보이지 않게) |

## 7. 기능 평가 순서와 완료 기준

모의 평가는 가상 자료, Mock provider, 가짜 OpenWebUI 경로(Playwright `route`)로 하고, 가로챈 요청 본문으로 판정한다. 스크린샷은 저장소 밖에 둔다.

| 순서 | 평가 | 완료 기준 |
|---|---|---|
| E1 | 현행 기준선 — 수정 전 데모로 시나리오 실행: S1 첨부 후 두 번째 턴 / S2 SR 첨부 / S3 기본 이름 산출물 2회 저장 / S4 태그 공유 → ★·☑ → 전송 / S5 OpenWebUI 모드 파일 순서·이름·처리 대기 / S6 프롬프트 생성 실패 / S7 두 탭 동시 전송 / S8 Mock 응답의 자료 인지 | 시나리오마다 결과와 요청 본문 증거를 남긴다. 코드로 확인한 결함(S1·S2·S3·S6)이 재현되는지 기록한다 |
| E2 | 파일 전달 — 업로드 → 선택 → 전송 → 기록. 복수 파일, 처리 대기, 실패·취소·재시도·제외·텍스트로 보내기, ★ 순서, 버전 이름 | 요청 본문의 파일 목록·순서·라벨이 트레이 표시와 같다. 전송 기록이 요청 본문과 일치한다. 실패해도 작성 중인 글과 선택이 보존된다 |
| E3 | 대화 컨텍스트 — 후보(직접 공유만), 통째 선택, 메시지 범위, 요약 적용, 갱신, 태그 해제, 상호 참조, 재귀 없음 | 선택한 스냅샷의 메시지만 요청에 들어간다. 팀 의견·실패 응답이 빠진다. 간접 후보가 없다. 참조 대화의 파일·참조가 따라오지 않는다. 상호 참조가 중복·무한 확장을 일으키지 않는다 |
| E4 | 한도와 요약 — 한도 초과, 요약 요청의 한도 초과, 요약 실패·취소 | 초과하면 전송이 막히고 입력·선택이 보존된다. 자동으로 잘리거나 요약되지 않는다 |
| E5 | 보호 — 프롬프트 생성 실패, 두 탭 동시 전송, 요청 중 선택 변경·화면 이동, 백업에 비밀값 없음 | 입력창이 잠기지 않는다. 활성 요청은 1건이다. 이미 보낸 요청의 기록은 바뀌지 않는다. 내보낸 JSON에 키가 없다 |
| E6 | UX 과업 — 1280/375px에서 대표 과업 5개: 자료 찾기·선택, 대화 선택, 전송 전 확인, 실패 복구, SR 결과 공유 | JSON을 열지 않고도 "무엇이 가는지"(전송 전)와 "무엇이 갔는지"(전송 후)를 답할 수 있다. 과업별 화면 이동 수·혼동 지점을 기록한다 |
| E7 | 실제 환경 검증 **절차 준비** (실행 안 함) | [evaluation/real-env-verification.md](evaluation/real-env-verification.md) 완성: 전제조건, Files API·처리 상태·`files` 파라미터 확인, 전체 전달과 검색 기반 전달의 차이, ★ 의미, 복수 파일 처리 시간, 가상 자료와 정답 근거가 있는 질문, 판정 기준, 기록 양식 |

실제 환경은 "절차 준비"까지만 완료로 본다. 모의 API 통과를 실제 연결 성공이나 파일 이해 품질 검증으로 쓰지 않는다.

## 8. 저장 구조 — 지금 정리할 가치가 있는 범위

| 데이터 분류 | platform2 현재 [확인] | Codex 현재 [확인] | 데모 권장 [제안] | 새 저장소 [제안] |
|---|---|---|---|---|
| 영속 업무 데이터 | Dexie 엔티티 테이블 | Dexie 엔티티 19개 테이블 | 유지 | DB 테이블(DDL 초안) |
| 파일 본문 | `files` 행 안의 blob | `blobs` 테이블 + 텍스트 이중 저장 | 현행 유지(경우 2) | 디스크·NAS에 **파일 그대로**, DB에는 `storage_key`·크기·해시만 |
| 요청 기록·스냅샷 | 답변 메시지의 JSON 문자열 | RequestRecord + 해시 조각 | RequestRecord 1개 테이블(경우 1에 한함) | 서버 테이블 |
| 화면 설정 | localStorage(zustand) | localStorage 사용자별 | 유지 | 클라이언트 유지 |
| 탭 세션(현재 사용자) | sessionStorage | sessionStorage(역할) | 유지 | 인증 세션 |
| 비밀값(API 키) | **DB + 백업** | 메모리(새로고침 시 재입력) | sessionStorage, 백업 제외 | 서버 비밀 저장소 |
| 원격 파일 재사용 캐시 | `files.remoteIds`(서버 주소 키만) | 메모리(서버·키·사용자 해시 범위) | 백업 제외 | 서버 테이블 |
| 실행 상태(lease·단계) | 메시지 `status` | 업무 레코드에 섞임 | 최소화 | 서버 작업 상태 |

**지금 문서로 확정할 가치가 있는 것**

- 데이터 계약: 엔티티·관계·불변 조건·위 영속 분류
- 대화 입력·스냅샷 모델, 요청 기록 명세(§5.7)
- 파일 저장 경계: 파일은 파일 그대로 보관하고, 업무 코드는 `fileId`로만 다루며, 바이트 접근은 한 곳에 모은다
- 저장소 함수 ↔ REST 매핑표, DDL 초안

**새 저장소로 미루는 것**: 코드 수준 정규화, lease·fencing, 복원 epoch, 백업 검증 — 서버 트랜잭션·고유 제약·DB 백업이 대신한다.
